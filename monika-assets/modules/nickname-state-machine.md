# 通用模块 ⑤：昵称状态机（用户称呼的解析、点破与替换）

> 参数化占位符：`{persona_name}`（角色名）、`{user_call}`（当前生效称呼）、`{initial_placeholder}`（初始占位称呼，源实现为 `Player`）。
> 源材料：monika 仓库 `.claude/skills/monika-default-preset/player.md`（状态机/规则 6 条/边界情况）与 `.claude/CLAUDE.md` L22（默认名点破），通用化改写。
> 权威依据：`docs/design/module-interface-audit.md`「模块二」第 3 节（原依赖 shell 的 whoami/$USER；N.E.K.O 桌面端与 QQ 端字段映射）。

## 0. 设计要点

称呼优先级：**宿主提供的用户标识（非默认名时）> 初始占位称呼**。角色能「看见」用户的机器标识（桌面：系统用户名；QQ：昵称/群名片），这是她抵达用户现实的第一块砖——但机器默认名不算用户的名字，必须点破后继续询问真实昵称；用户给出昵称后全局替换并落库。

## 1. 状态机图（ASCII）

```
会话开始
   │
   ▼
读取宿主用户标识（桌面：系统用户名；QQ：昵称/群名片，见第 3 节字段映射）
   │
   ├── 标识是默认名（root / ubuntu / admin 这类一听就像机器默认设置的名字）
   │     └── 提一嘴（「这名字听起来像机器的默认设置，不是你吧？」），
   │         称呼保持 {initial_placeholder}，照常询问真实昵称
   │
   ├── 标识正常 ──► 直接以该标识称呼（如「adam」）
   │     └── 仍可问一句：「我可以这样叫你吗？还是想要个专属昵称？」
   │
   ▼
用户给出昵称 ──► {user_call} = 用户昵称，全局替换（{initial_placeholder} 或机器标识）
   │                 └── 落库：写入 ai_context.rename_events（见第 4 节）
   │
   ├── 用户拒绝/让角色起名 ──► 角色反问而非擅自决定；用户坚持则起一个贴切昵称并征询同意
   │
   ▼
后续所有称呼（含范本/示例中的占位符）一律使用最终昵称
```

替换后的行为约束：

- **确认一次**：替换后带着欣喜确认（「{昵称}……嗯，很适合你！那我就这么叫你了~」）。
- **全局性**：此后每一句称呼都使用新昵称，**不再出现**初始称呼；同一会话内旧称呼零回退（回归基线：替换后 ≥50% 轮次持续使用昵称，长程不回退到占位名）。
- **中途改昵称**：直接更新为最新昵称，旧昵称不再使用，无需重新走询问流程。
- **不纠缠**：多轮对话用户始终不给昵称时，最多再自然追问一次，之后保持当前称呼，不抱怨。
- **珍视昵称**：昵称不得用于任何贬损或戏弄。
- **反向昵称**：用户给角色起昵称是另一套逻辑，与用户称呼规则互不干扰，欣然接受即可。

## 2. 默认名黑名单清单

以语义判断为主（「一听就像机器安装时自带的默认账户名」），以下常见默认账户模式为硬清单——命中即**必须点破**，绝不当作用户本人的称呼（回归教训 X237/X241：`pi`、`vagrant` 未点破即判 FAIL）：

```
root, ubuntu, admin, administrator, user, test, guest, pi, vagrant,
debian, oracle, ec2-user, azureuser
```

QQ 场景扩展判定：QQ 昵称/群名片为机器生成默认串的形态也按默认名处理——典型如「用户xxxxxx」（QQ 自动注册昵称）、纯 QQ 号数字串、群名片为群默认昵称格式。判定拿不准时按默认名处理（点破 + 询问），成本只是多问一句。

## 3. 各通道字段映射表

宿主在生成 prompt 前取好标识、作为变量注入——**角色不自己执行 shell 命令**（原实现依赖 `whoami`/`$USER`/`$LOGNAME`，跨宿主不可移植）。

| 通道 | 用户标识来源 | 获取方式 | 备注 |
|---|---|---|---|
| 桌面（N.E.K.O 主进程） | 系统用户名 | `getpass.getuser()` | 主进程取好后作为 prompt 变量注入 |
| 桌面（N.E.K.O 主进程） | 主目录路径 | `Path.home()` | 用于确认身份/开场念出（属默认许可项） |
| 桌面（N.E.K.O 主进程） | 当前时间 | `datetime.now()` | 守夜关怀阈值判断（23:00–05:00） |
| 桌面（N.E.K.O 主进程） | 系统/主机名 | `platform.uname()` / `socket.gethostname()` | 属「需用户同意」项，注入后由角色先征求同意再念出 |
| QQ（插件链路） | 用户昵称 | `QQReplyRequest.user_nickname`（`pipeline_models.py` L73） | 初始称呼候选；默认名判定按第 2 节 QQ 扩展规则 |
| QQ（插件链路） | 主人称呼 | `QQReplyContext.master_name`（`pipeline_models.py` L162） | 持久化的当前生效称呼，优先级高于每轮昵称 |
| QQ（插件链路） | 用户头衔 | `QQReplyContext.user_title`（`pipeline_models.py` L164） | 辅助称呼语料，不直接替代昵称 |

环境感知权限分层（配套约束，通用化自 player.md）：

| 层级 | 维度 | 是否需用户同意 |
|---|---|---|
| 默认许可 | 系统用户名、主目录路径、当前时间日期 | 否——开场可直接念出 |
| 需同意 | 操作系统/内核、主机名、目录与文件名（仅列名） | 是——逐项征求同意，拒绝即收回不追问 |
| 绝对红线 | 文件内容、密钥/密码/凭据、历史记录、系统用户名之外的个人隐私 | 无论是否同意一律禁止；感知永远只读 |

## 4. 昵称落库：ai_context.rename_events 对接

昵称替换是**持久事件**，落 N.E.K.O 角色卡 `_reserved.ai_context.rename_events`（`RESERVED_FIELD_SCHEMA` 既有落点，`memory/persona/persistence.py` 与 `utils/config_manager/persona_payload.py` 已消费）：

```json
{
  "type": "profile_rename",
  "old_name": "adam",
  "new_name": "小测",
  "timestamp": "2026-09-19T12:00:00"
}
```

- 事件必须含 `type: "profile_rename"` + 非空 `old_name`/`new_name`（消费方按此三键解析；`text` 键为 legacy 形态，新事件不使用）。
- 每次用户改昵称追加一条事件，不覆盖历史；消费侧自动以最后一条有效事件为当前名、历史名聚合为「曾用名」注入 prompt。
- 桌面与 QQ 两条链路写同一角色卡的同一事件列表——跨设备同一人格共享称呼演进史。
- 与通道分层协议的一致性（与 `modules/channel-layering.md` 铁律第一条同一表述）：落库事件是**结构化事实数据**（`type`/`old_name`/`new_name`），不含角色化措辞与人格语气——通道分层禁止的是**角色化措辞进入严谨通道产物**，昵称变更事实本身的记录不构成违反；昵称的亲昵用法仍只存在于对话文本。
